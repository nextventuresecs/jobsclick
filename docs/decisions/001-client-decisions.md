# Client Decisions & Architectural Directives

This document records confirmed client decisions and deployment targets that override or refine `docs/PRD.md`.

## 1. Deployment Platform: Railway
- **Primary Deployment Target:** **Railway** (`https://railway.app`).
- **Architecture on Railway:**
  - **Service 1 (`apps/web`):** Next.js App Router frontend, public domain mapped, internal reverse proxy for telemetry (`/monitoring`).
  - **Service 2 (`apps/api`):** NestJS on Fastify adapter, internal networking connection to Redis and Supabase.
  - **Service 3 (`apps/worker`):** Plain Node background process executing BullMQ queues, connected to Railway Redis.
  - **Redis Plugin / Service:** Managed Redis running on Railway for BullMQ queue state and Upstash rate-limit fallbacks.
- **Environment & Ingress:**
  - Services communicate via Railway private networking (`.railway.internal`).
  - Public ingress is exposed only for `apps/web` and `apps/api`.
  - Background worker `apps/worker` has no public HTTP port.

## 2. Scope & Features
- **Release verification:** GitHub Actions runs CI on pushes and pull requests. An authorized manual run on `main` verifies staging deployment identities before production can request approval. The [staging runbook](../runbooks/staging-environment.md#7-railway-release) covers the staging-only test and promotion.
- **Web fonts:** Builds use locked Inter and Noto Sans Devanagari packages for English and Hindi without a Google Fonts request at build time.
- **Shared web buttons:** Use a 48 × 48 CSS pixel minimum target, 16px text, visible keyboard focus and reduced-motion support. Use existing Jobsclick palette tokens.
- **Queue and privacy checks (BULK-02/03, JS-03, INT-03):** Live queue publication must be acknowledged, and pending resume jobs coalesce per seeker. Bulk-import queue results omit contact data, and inquiry contact access requires an audit write. Sentry telemetry strips email-verification URL tokens and restricts the API test endpoint to staging admins.
- **MVP + Full Extras + Hindi:** All user-facing copy in English and Hindi (`next-intl`), with Hindi rendering support in PDF resumes (`@fontsource/noto-sans-devanagari`).
- **Hindi public routes (AUTH-07):** The first response from `/hi` and `/hi/jobs` renders Hindi HTML, including for visitors without a locale cookie or with an English preference. The Hindi URL stays visible and crawlable.
- **Public job discovery and profile editing (JOB-02, JOB-03, JS-02):** Home links to existing audience entry points and shows available listings from the public API. The shared header and footer preserve the selected language in their links. Jobs search preserves filters in the URL, distinguishes empty results from service errors, and filters/pages through server results (including `employmentType`). Job details present one Apply control for open listings. The seeker profile editor groups the existing fields into three steps and submits the existing payload from the final step.
- **Location scope (2026-11-27 — launch is India-level, supersedes MP-only):** Launch data is India-level, superseding the prior MP-only scope so national state, district, and PIN reference tables (`states`: 36, `districts`: 785 LGD + manual gazette patch rows for Ladakh/Sankoo/Markapuram, `pincodes`: 19,586) ship at launch while marketing and sales focus may still prioritize Madhya Pradesh. Reference tables (`states`, `districts`, `pincodes`) are `service_role`-only per ADR 0002 (RLS enabled, no `anon`/`authenticated` policies); reads go through cached `GET /locations/*` API endpoints. Profile tables (`job_seeker_profiles`, `business_profiles`, `institution_profiles`) add nullable `state_code`, `district_id`, and `pincode` with no backfill and keep existing free-text address columns. `jobs` adds nullable `state_code` and `district_id` (no `pincode`, no `search_jobs` change). `location_nodes` (P3 GEO) stays untouched. Institution roster ownership sits with client operations / MSME Department data holders (PRD D8), not engineering. Hindi labels, RLS, and migrations touching existing tables remain subject to human review before applying.
- **Onboarding, copy, and deferred/small UX scope:** Employer onboarding routes to the employer workspace (business profile, then post job). Institution onboarding routes to bulk import, with the placement dashboard gated as P2 (contact/inquiry flow until P2). Use placeholder copy for support and marketing until client-supplied text arrives. Do not build voice search/input (deferred/out of scope). Defer GPS/location-node matching to P3. P2 wallet messaging will lead with the confirmed "10 free applications" entitlement. Apply Undo is scoped only if implementation effort stays under one day. Auth/OTP, payments, and DPDP consent text (legal review required) remain human-review-only.
- **Release verification & user trials:** Use the Railway staging environment as the isolated preview, keeping `X-Robots-Tag: noindex, nofollow` and staging tripwires rejecting production keys. Release sign-off requires Hindi copy review by 2 native speakers from the client team, 2–3 TalkBack testers arranged with the client, and task trials with 5 students from an Indore college or ITI placement cell on a ₹8–10k low-end Android device.
- **Database & Authorization (#131, ADR 0002):** Supabase / PostgreSQL accessed via server-side privileged workloads for MVP, evolving toward least-privilege DB roles (Option 3). Application-level authorization (API guards, server-derived `AuthorizationContext`, and repository tenant scoping) is the primary runtime tenant-isolation boundary; `anon` and `authenticated` have zero base-table grants and enabled deny-all RLS to block direct DB access. Automated authorization tests provide regression protection, not a runtime second boundary. Sensitive financial/PII mutations run in audited functions with restricted execution and pinned `search_path`. See [ADR 0002](../adr/0002-authorization-model-api-enforced-deny-all-rls.md).
- **OAuth (AUTH-01, AUTH-05):** The API issues a session only after Supabase Auth confirms the provider session and its email. Existing account matching must agree with the confirmed email.
- **Browser sign-in and CSP (AUTH-01, AUTH-05):** The browser redeems the Google redirect code with Supabase using PKCE and sends the resulting access token to the API for verification. Next.js middleware sends a fresh CSP nonce for each rendered response. The policy allows the configured API origin, and Fastify permits browser requests from the configured web origin.
- **Observability:** Sentry with DPDP-compliant Zero-PII scrubbing and distributed trace propagation (`web` -> `api` -> `worker`).
- **Worker error telemetry:** Record queue, job, trace and attempt metadata for exhausted retries. Exclude the job input and notification provider response bodies from logs and events.
- **MVP bulk intake (BULK-01–05):** Forms and downloadable templates start empty. Authenticated intake accepts CSV and Excel `.xlsx` and converts the first worksheet to CSV under upload and expansion limits. Aadhaar columns are rejected before storing the CSV or queuing its private storage reference. The worker ignores Aadhaar fields in legacy jobs. Invitation waves require a completed import and a separate cost preview.
- **First-time resumes (JS-03):** A missing private resume object queues PDF generation. While generation is pending the web client polls the authenticated endpoint. Storage errors remain retryable worker failures.
- **Notification dispatch (NOT-02, AUTH-03/04, BULK-03):** Staging and production require a provider acknowledgement before reporting a dispatch as accepted. Staging allowlist blocks and provider failures return a failure without a synthetic receipt. Provider acceptance does not confirm inbox or handset delivery.
