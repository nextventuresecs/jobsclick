# ADR 0002 - Opaque server-held provider sessions

Status: draft implementation; team approved this direction and the draft limits on 2026-11-17. Human auth review is still required before merge or hosted enablement. Requirements: AUTH-01, AUTH-05, AUTH-06; PRN-03. No provider configuration changes are authorized by this ADR.

The browser holds an opaque HttpOnly/Secure cookie. Supabase access/refresh credentials stay encrypted in server-side Redis. Supabase remains the token issuer. The team requires credentials off the browser entirely, plus a server-enforced absolute deadline independent of provider refresh: 7 days for ordinary accounts, 12 hours for admin/MSME-admin accounts, and 15-minute provider access tokens with reauthentication at the absolute deadline.

`@supabase/ssr` with HttpOnly access/refresh cookies would be simpler and reduce Redis/cryptographic operational burden. Those credentials still reside in browser cookies. The selected opaque-store design implements the team's stronger storage preference and central revocation/concurrency controls; it is not a claim that cookie-based Supabase sessions are generally unsuitable.

Redis is now an authentication availability dependency. **Every protected request fails closed with 503 when session storage, revocation state or authoritative identity checks are unavailable. This explicitly includes admin, payment and wallet routes.** No cached role cookie, supplied user ID, stale credential or queued/offline financial mutation bypasses that decision. Public discovery may remain session-free. Disabled payment/P2 routes remain disabled.

Refresh must use one server lease across instances, preserve the original deadline and fence logout/stale responses. Ambiguous refresh outcomes require reauthentication rather than reusing the refresh token. Application-store revocation is separate from provider session revocation; durable provider sign-out/retry and current application/provider status checks must be integrated before cutover. S6 must prove a real HTTP request is rejected after a provider ban between claim and the next request, not merely test a mock user response.

Production prerequisites remain: Redis TLS/private ingress and narrow ACLs; protected encryption keys with an explicit key ID and reviewed rotation/re-encryption procedure; no credential logging/backups without protection; capacity/availability monitoring; current provider-session and explicit login-method enforcement. No unreviewed key-rotation design or deployment setting is enabled. Keep the new session path unregistered until its API/BFF lifecycle and outage denial tests pass.

2026-11-18 native coverage: the existing server provider adapter rejects copied, unexpired JWTs after actual local/global GoTrue logout and provider identity deletion, while preserving the other session after local-only logout. The focused provider/store/native run passes 55 tests. No adapter implementation changed and no artificial red was claimed for already-correct behavior. The application must still compose this server check with opaque-store resolution and current application status on every protected request; store-only resolution is insufficient. API/BFF logout, durable retries and HTTP guard/workspace cutover are still pending S5/S6. Evidence: `docs/auth/evidence/followup/overnight/provider-revocation.txt`.
