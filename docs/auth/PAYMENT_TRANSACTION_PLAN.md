Recovery procedure for the future reviewed rollout:

1. If the gateway capture succeeded but local settlement failed, do not capture again or mark the payment settled manually. Use a verified callback/webhook redelivery with the same canonical order/payment facts. The database locks the order and either atomically settles it or returns the existing receipt. Tests prove failure leaves created/authorized local status and no partial grant/ledger/audit; actual backend termination leaves sponsorship grant state absent and retryable.
2. If the local payment is captured without a receipt, stop with PAYMENT_LEGACY_RECONCILIATION_REQUIRED. For old sponsorship references, SPONSORSHIP_LEGACY_PAYMENT_REQUIRES_RECONCILIATION also stops processing. A human must compare gateway evidence, owner, purpose, target, amount and prior ledger/grants in a backed-up disposable rehearsal before approving a separate reconciliation migration. Do not guess grants from status, auto-backfill receipts or delete persistent records.
3. Conflicting target/key/fingerprint or wallet-to-sponsorship reuse is a denial, not an instruction to generate another key. An exact valid retry returns the same receipt/grant. Required audit failure rolls back the financial change.
4. Monitor verified redelivery failures and escalate ambiguous external outcomes for review. No automatic reconciliation/outbox worker or retry of an ambiguous gateway mutation was added here. Provider outage, refunds/chargebacks, invoice delivery and live gateway lifecycle were not exercised; do not claim cross-service zero-gap atomicity.
