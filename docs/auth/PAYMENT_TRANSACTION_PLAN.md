# WAL-03/05 local payment transaction draft

2026-11-18. The user authorised resolving the previously stopped payment contract. No hosted changes, real gateway capture, feature enablement or S6 work is authorised. The two existing attacker assertions stay intact.

1. Database contract: private append-only payment-grant receipts keyed by canonical payments UUID, scoped request key and request fingerprint. A service-only invoker wrapper calls the private definer transaction with empty search_path. Lock current actor, canonical payment, institution and its UUID-linked students. Reject wrong owner/status/purpose/currency/amount, wallet payments, ambiguous references, conflicting keys and unclassified legacy use. Grant, receipt and mandatory audit commit or roll back together. Exact retries return the same grant; a changed request cannot reuse the payment. Old references are not backfilled or guessed.
2. API integration: production uses one RPC; the disposable JSON test adapter gets rollback semantics solely to preserve its service regressions. Native transaction/termination tests supply the database proof. Phone/email/Google and unrelated auth contracts remain unchanged.
3. Capture settlement: verified gateway facts must be checked against the locked order. Database captured status, wallet credit or bound sponsorship grant, receipt and audit commit in one transaction. External gateway capture cannot be part of the PostgreSQL transaction; a failed local settlement leaves the order retryable on verified webhook redelivery/reconciliation, never terminally marked settled without its grant. Captured legacy rows without receipts require review. No generic automatic retry of ambiguous gateway mutations.
4. Verify native concurrency, write/audit failure, actual backend termination, client/direct-write denial and exact retry. Then original service tests, gateway/webhook regressions, full package typecheck/lint, bulk/workspace/application regression and disposable cleanup. Source and evidence commits stay separate; generated snapshot refresh is mechanical.

Pricing and tax constants remain the existing 150/100/70 INR bands and 18% calculation. New sponsorship payments require trusted order metadata purpose=sponsorship and institutionId; wallet packs cannot fund a second sponsorship grant. Public sponsorship checkout/order creation remains disabled and is not introduced by this remediation. Human payment/migration/RLS review remains necessary before merge or enabling the existing payment flag.
