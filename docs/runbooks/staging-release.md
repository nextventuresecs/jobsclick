# Railway release verification

Use the [Railway release checklist](staging-environment.md#7-railway-release) for an authorized staging run or production promotion. Pull requests, including drafts, and ordinary pushes run verification without starting a deployment. Keep Railway Source auto-deploy off for API, web, and worker in both environments.

CI sends only tracked files from the workflow commit to Docker and Railway. Staging checks the exact deployment IDs for all services. API `/health` and web `/api/health` must return HTTP 200 with `status: ok` and the requested deployment ID. The private worker must report a fresh readiness heartbeat after connecting to Redis and the queues. The same checks must pass twice in succession. Production also requires the GitHub `production` environment approval.

Before running the release, confirm the approved application baseline, `SUPABASE_CA_CERT` secret, and `PRODUCTION_PITR_VERIFIED` (for production) are configured. Staging and production jobs run `--dry-run` migration preflight before applying `supabase/migrations/` with strict TLS (`SUPABASE_CA_CERT`, `NODE_ENV=staging|production`), followed by Railway deployment verification. See [Database Deployment & Migration Safety Runbook](database-deployment.md) for full details. Confirm staging Redis and the health origins on Railway, and set the GitHub `staging` environment variables `STAGING_API_URL` and `STAGING_WEB_URL` if they differ from the defaults. Store the separate environment-scoped Railway project tokens in the corresponding GitHub environment.

Set `NEXT_PUBLIC_APP_ENV=staging` for the Railway web build and `APP_ENV=staging` for its runtime. Staging `robots.txt` permits crawling so search engines can read `X-Robots-Tag: noindex, nofollow`. The staging sitemap contains no URLs.
